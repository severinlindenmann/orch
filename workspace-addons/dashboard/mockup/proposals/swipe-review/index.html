Swipe review

Everything that waits on you, one card at a time. Right = Looks good, left = Don't do, down = Comment (voice or text). The middle of the card is the thing itself: a screen, a draft, a file, a link. Tap it to make it bigger, open it, or comment on one spot.

Phone app (6 states, one live) Workspace dashboard (live, keys work) Ticket page: Decisions tab Without the dashboard (orch review)

Research: what others do, what we take

WhereWhat they learnedWe take
Tinder, Bumble (card stacks)One decision at a time is fast and calm. A stamp while dragging tells you what will happen; let go early and it springs back. Buttons under the card for people who don't swipe.One card, the stamp, three buttons, the card behind peeks out.
Apple Mail, Gmail swipe actionsSwipes fire by accident. Fix: a clear distance (about a third of the width) or a fast flick, and Undo right after.30 % width or a flick; Undo toast 5 s; Z on the desk.
Superhuman, Linear TriageOn a computer, triage is a keyboard job: one key per answer, preview with Space.← ↓ → and Space; drag still works with the mouse.
Before/after sliders (photo apps, Percy / Chromatic visual tests, GitHub image diff)A change is judged fastest next to what was there: a slider for screens, side by side for text.Slide line in the big view, Before · After · Both on the card (no slider on the card, it would fight the swipe).
Polls, A/B design reviews (Figma voting, Lyssna preference tests)Choosing is easier with all options side by side and one clear pick; comments are about one option.Options card: side by side on the desk, stacked on the phone; comment “about C”.
Photo grids, Tinder “rewind”, mail inbox listA stack hides what is left; people want to see the whole pile and go back.“All cards” overview + jump; answers can be changed.
Figma, Markup, GitHub review“Change this” is much clearer on the spot than in a sentence.“Comment on a spot” in the big view.
WhatsApp voice notes (and our messenger)Hold to talk is the quickest way to say a long thing on the phone.Hold to talk in the comment sheet, written out like the chat does.
Accessibility (WCAG 2.2: 2.5.1, 2.5.7; iOS VoiceOver)Every swipe needs a one tap way, a drag is never the only way; screen readers need named actions.Buttons always there; VoiceOver actions “Looks good / Don't do / Comment”; Reduce Motion = no fly-out.
Known risk: “rubber stamping”Fast stacks tempt you to approve without looking.Each card says what happens when you approve; risky ones still ask a second time; the stack stays short (what waits now).

Built into orch: works without the dashboard

Review is part of orch itself, not an add-on: nothing to install or turn on. orch serves its own small Review page from the same design system, so it works with the CLI only, on a server, or with the dashboard. See the page orch opens by itself →

You useYou get the review
Only the CLI / terminalorch review opens the page in your browser and prints the link (helpers can also print or send the link).
A server without a screenThe same link plus one copyable line to reach it from your laptop (ssh -L …), or over the private network when that is on.
The dashboardThe same page as “Review” (Home → Review all), with the sidebar.
The phoneThe same stack in the app (yellow row on Chats, push).

Whichever door you use, the answer lands in the same place on the ticket.

$ orch review
8 things wait on you (2 needed before Friday).
Open: http://127.0.0.1:47211/review?k=4f9c2e…   works on this computer until 18:30
On a server? From your laptop: ssh -L 47211:127.0.0.1:47211 you@server   then open the link.

# a helper puts a card in the stack and waits for the answer
$ orch review add DT-45 --choose "Home: which layout?" \
    --option "A=As today:files/home-a.png" --option "B=Recent changes first:files/home-b.png" --suggest B \
    --option "C=Questions first:files/home-c.png" --then "I build the one you pick. You check it before it goes live."
$ orch review add DT-41 --draft "What changed today" --before files/home-old.png --after files/home-new.png --ok "Build it"
$ orch review link            # the link to send you (chat, phone, terminal)
$ orch review wait DT-45      # prints the answer when it comes:
Use C with 2 changes: questions on top; month in the heading. (Severin, phone, 10:42)
  • The link has a random key, works only on this computer by default, and runs out (default: end of day). Answers through it count as you (the person chosen in orch), like the dashboard.
  • Helpers learn it from orch's own helper instructions: “to ask the owner to decide, use orch review add; never decide for them”.
  • Without the dashboard there is no ticket page, so the Review page has an Answered list, and orch ticket show DT-45 prints the same Decisions block helpers read.

Where the answer is kept

Every swipe is kept on its ticket, so you can come back later, and helpers read it without guessing. See the ticket page draft →

  • Ticket → Decisions tab (new, fixed place after Tasks): one card per answer, newest first, showing what you saw then (options with the taken one marked, before/after, pins in place), your answer, your words (voice with its text, typed text, the spots you marked), who, when, phone or dashboard. “Open as you saw it” opens the same big view, read-only.
  • What you saw stays as it was: orch keeps a copy of exactly what the card showed (screens, text, options) next to the answer, plus its fingerprint. A later file change can't move the answer onto something else, and “View reviewed version” always shows the old one.
  • On top: “What applies now”: the current instruction in plain words (which option, which changes, what happens next). Older answers stay below with what came of them (“Done: led to the 3 layouts”, “Replaced by the answer above”). Changing an answer never deletes the old one.
  • Activity: the same answer as one plain line (“Severin took C on …: put the questions on top; on C: show the month here. (phone)”).
  • For helpers: the answer lives in the ticket's existing question list (no new store), plus a ready-made one-sentence summary written by orch from the parts, so a helper reads one line and finds the details (voice file, transcript, pins) next to it. The ticket's own command prints a “Decisions” block in the same words.

My recommendation

  • Put in the stack: drafts, Check results, helper plans that need a yes, links before they go public. Questions with several choices stay normal question cards (a swipe can't pick option B).
  • Left word: “Don't do”, but “Send back” on Check results (that is the word the ticket already uses).
  • Swipe up = Later (added after the challenge: an honest “not now”).
  • A comment never approves. To approve with changes on options, the sheet has its own button “Use C with these changes”.
  • Build: built into orch (no add-on): one widget in the master design system (UI.swipeDeck, used by every page here), the Review page orch serves itself, the same page inside the dashboard, one SwiftUI screen in the app. Answers use the same paths as today's Looks good / Send back and the question answers, so nothing new on the wire.
