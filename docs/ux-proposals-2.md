# When work stops: six drafts for setup and add-ons

**ORCH-1855 · 24 November 2026. Try Insights first, then Pull requests.** One failed read can hide numbers a manager was just looking at. A failed check can look as if someone is already fixing it. Both drafts help a person decide whether to wait or act, without starting more work.

These are independent experiments, ranked after one challenge from Claude Opus 5.5. Each slug names a `f61-ux-<slug>.md` sprint job. The last column is a test for the builder, not a result from a user study.

| Draft | Before | After | What would count as better |
|---|---|---|---|
| 1. Insights: keep the last good reading (`insights-retry`) | After a successful overview, a failed skills-list read calls `showMessage`, hides the overview and clears it. The generic read error has no retry button; another refresh is scheduled in 30 seconds. | Leave unaffected figures in place. Beside the failed section, show when it was last read and **Try again**. With no prior reading, show an error, not zero activity. | Fail just one list, retry it and keep the selected tab. Distinguish first load, true first-day empty, transient failure and lost access. Never show prior private values after access is lost. |
| 2. Pull requests: say who is actually repairing (`repair-status`) | The billing sample says “Checks failed: lint. Waits for a helper place.” `repair_note` infers the wait from ticket status; `_runs` also treats an unreadable list as empty. | Keep the failed check first. Show a known live helper, “No helper is running on this ticket”, or “Couldn’t check whether a helper is running”. Link the ticket where there is one. | With the *same* failed check and open ticket, a live run, a successful empty read and a failed read produce three different answers. Never claim a queue place without queue evidence. |
| 3. Factory: recover a stalled run from anywhere (`factory-recovery`) | The home notice says pickup is off; a stalled order tells the person to start orch “on this computer”. That does not tell someone on a phone what to do. | Name the effect: “This run is waiting because Factory isn’t running.” Point to a verified workspace recovery action, or say who can run `orch factory start` in the workspace. | From a remote signed-in browser, identify which workspace needs attention. ### What the second reader changed

Opus kept all six but put continuity and false repair status ahead of setup. We adopted that order. In Insights, retaining data is appropriate for a transient error, **not** loss of authorization. In Factory, a plausible-looking restart button is worse than a truthful instruction: the current dashboard `addon.start` invokes `start --no-open` for the workspace. In Browse, the broker reopens the site's origin, not the person's exact page; don't promise the site forgot their activity. For Automation, the CLI resolves a new repeat's zone before saving it; “always UTC” would introduce a new error. For install, the observed inconsistency is not evidence of abandonment: start with the success message and first-step examples, not a wizard.
