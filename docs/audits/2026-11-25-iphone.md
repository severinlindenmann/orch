# iPhone review: delivery, pairing and accessibility (ORCH-2119)

At `fdce6363b`, three failure paths deserve attention first: the phone can discard queued work after a credential read error, promise to keep a message it has not saved, or show a different review decision from the one the workspace received. Each finding below has a fix ticket and a proposed regression check. These are source traces, not observed device failures.

| Priority / ticket | What happens and why | What the fix needs to demonstrate |

On pairing, `AppModel.swift:382–391` advances even if storing the credential failed. An unavailable credential is not evidence of sign-out. | Inject an unavailable read on an installed phone with queued work, then a successful read: same account, snapshot and queue. **Controls and challenge.** Claude Opus 5.5 challenged the failure scenarios without device or service access. After-first-unlock protection does **not** imply that an ordinary screen lock makes the token unreadable. Backgrounding submits the snapshot and index and waits for both writers; that mitigates suspension, not a failed write. A later successful full-index write can repair the queue. Existing `M0Tests` cover backoff, overlapping flushes and a lost send response; `ReviewStackTests` cover edits before sending and after acknowledgment, not delivery with an uncertain outcome. Stable client IDs prevent duplicate messages; they do not make a changed answer replace the original.

**Security and accessibility scope.** Credentials use device-only Keychain storage. [PR #3044](https://github.com/severinlindenmann/orch/pull/3044) already covers transport, pasted links and updating the credential in place; it does not change the startup nil/wipe branch or require pairing to honor the save result. On the reviewed receive paths, `IncomingCheck.shown` rebuilds message bodies from checked envelope data; held/refused messages do not enter the ordinary list. Unsigned compatibility is explicit. Review links are parsed by `CardOpenLink` and opened by a button, not by receiving a message. This is not a certification of all relay traffic.

Question choices expose their name, recommendation and selection in `QuestionCards.swift`; the existing `docs/images/iphone-questions.png` illustrates why the recommendation matters but cannot establish spoken output. The started receipt itself announces “Delivered”; there is a separate working-status line in `ChatScreens.swift`, so this is not evidence that VoiceOver loses the whole chat's working state. The contradictory Play/Pause announcement already has ORCH-2064. No duplicate job was filed for it.

No simulator, build, live pairing, VoiceOver session or XCTest run was performed. The six fix jobs carry the regression checks into their respective changes; this review changes no app behavior.
