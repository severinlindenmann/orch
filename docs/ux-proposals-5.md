# Tell me what my next action will actually do

**Round 5 · ORCH-2056 · 25 November 2026.** Try the Factory pause control first. Someone deciding whether work can continue without them needs to distinguish “I opened a conversation” from “I changed how Factory works.” The existing control looks like the second and does the first.

### Evidence and limits

Baseline `8b11ad253`. Compared the earlier four reports and the master gallery, `DESIGN.md`, tokens and UX checklist. The master declares a dark color scheme; the goal here is a visible keyboard destination against the existing surfaces, not a new theme. The timing above is a single fixture observation, not a performance benchmark. Master `motion.js` waits before calling `close`; master `overlay.js` separately schedules native close. Dashboard `app.js` and `orch_ui/static/fileviewer.js` both use that path. Evaluate native modal state, active element and the [dialog keyboard pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), not a screenshot of a fade.

Factory evidence: `orch_factory/web/factory.js` (`askRow`, `toChat`, `askDialog`), `orch_factory/autopilot.py`, and dashboard `pages/chat.js` (`chatSayRequest` and its draft-preserving handler). Focus evidence: `pages/livewall.js` (`liveWallBands` → `liveWallBand`, run with synthetic rows and an element-tree recorder); the issue is **after** a successful match, not round 4's missing status alias, collection limit or refresh. No real helpers or remote recipients used.

Read `install.ps1`, `cli.py` (`_env_root`, `_init_guard`), `cli_diag.py` and `nextstep.py`; ran checkout help and reproduced the init refusal (exit 2, no local `.orch`) under a disposable strict home on macOS. This is not a Windows execution. The installer itself is not another draft: first-run routes, Path and restoration were already covered. Reviewed `mobile/OrchMobile/Views/VoiceBubble.swift` and `docs/images/iphone-questions.png`; the latter shows dark phone typography, **not** voice playback. The iPhone finding is from the Swift accessibility attributes, not a claim about exact VoiceOver speech. No simulator or Xcode build.

### What the challenge changed

Claude Opus 5.5 ranked misleading diagnostic help highest. Keep that change narrow: `diag delete` already names its effect; don't add a confirmation ceremony or run it against real data. For Factory, verify the receiver's **selected item**, not just the disabled box, without implying a leak. For Focus, expose matches temporarily, not every folded group forever. The reviewer questioned whether the dialog delay was perceptible, so we measured the promise and native close separately; the still-open dialog is the defect, independent of machine speed. On iPhone, check the accessibility label and value together rather than renaming only the icon.

Each slug maps to `f64-ux-<slug>.md`. Builders produce working alternatives for comparison, not releases. No change to run policy, sharing rules, ticket storage or platform support is proposed.
