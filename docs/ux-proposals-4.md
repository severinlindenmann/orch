# Keep the right ticket in reach

**Round 4 · ORCH-1966 · 24 November 2026.** Start with the missing Focus request, then Factory refresh. In the first case someone can be told there is nothing to do when a helper is waiting; in the second, the page moves the keyboard away just as the person is about to act. Neither needs a new screen.

Each slug names one `f63-ux-<slug>.md` draft builder. The tests below are decisions for the owner to make on working before/after pairs, not claims about people we tested.

| Priority / draft | What happens now | Build this after; how to tell it works |
|---|---|---|
| 1. **Find the waiting helper** (`focus-last-request`) | Focus sorts run-record filenames and reads only the first 200 **before** checking who needs attention. In a synthetic directory the only waiting helper produced **0 rows in position 201, 1 in position 200**. This is about run records, not just having 201 tickets. | Let the person see the real request and open its ticket, without a false “Nothing needs you here.” Move the same record across the boundary; the answer must stay the same. Stopped helpers and hidden conversations must stay out. |
| 2. **Keep my place in Factory** (`factory-refresh-place`) | On a changed home reading, the visible page calls the same `render()` as navigation: loading shape, new nodes, `page-enter`, then focus on the heading. The busy check protects typing and open dialogs, not a focused order link. | While reading order A, let order B change without sending the keyboard back to the title. Insert a row above A; pressing Enter must still open **A**, not the item at A's old position. Navigate deliberately and the new heading should still receive focus. |
| 3. **Choose among similar ticket names** (`select-by-prefix`) | The dashboard's **Replaced by** picker prefixes options with the ticket key. The master listbox tests each printable key separately against the start of the label. With 120 `SALES-…` choices, typing `SALES-097` is not a way to reach ticket 97. In the shipped stylesheet order the ordinary trigger border also falls back from the intended input token to the weaker border token. | Use prefix navigation on the existing list; visibly focus the candidate without committing it. Compare `SALES-009` with `SALES-097` and long titles sharing their first 60 characters. Read the full option without hover at 320 px. Use the existing input edge on dark cards, not a new palette. Tab, Escape and explicit selection must remain distinct from moving the ticket. |
| 4. **Filter Focus by what needs me** (`focus-needs-filter`) | An unstarted ticket with a result to check joins the Focus **Needs you and working** band. With the wall's own model, filtering that entry by `Check` returns 1, `Needs you` returns 0. The filter advertises search by status. | Find the same ticket by either phrase while keeping its specific label **Check**. With 119 unrelated sessions and one such ticket, clearing the filter restores the original groups and pins. A working helper alone must not match just because it shares the band. |
| 5. **Finish a reduced-motion swipe without a spring** (`phone-swipe-settle`) | On iPhone the Needs you row already offers Hide through VoiceOver and a context menu. Both shared swipe modifiers explicitly animate release and close, unlike the Reduce Motion branch used for chat scrolling. | Keep movement under the person's finger. With Reduce Motion on, releasing gives the same final open/closed/hidden result immediately; with it off, preserve the existing spring. Test both the question row and a chat row: a long fling must never delete a chat. |
| 6. **Know what finished installing** (`windows-restore-result`) | After installing the core, PowerShell checks `update --after-install`. On a nonzero exit it prints a restore warning and `orch update`, then still ends with “orch is installed” and directions to run `orch init`. A returning user gets two different next actions. | Lead the final summary with both facts: “orch is installed. We couldn't finish restoring your add-ons.” Give the applicable recovery command in the project folder; don't suggest setting the workspace up again. Compare a stubbed nonzero restore with a successful first install. Don't guess which add-ons were restored. |
| 7. **Find a ticket Focus couldn't open** (`focus-open-next`) | In a disposable workspace `orch focus open t_absent1 --no-open` refused with “Give a ticket id like t_ab12cd or its key like DM1-12.” The supplied ID already has that shape. The core resolver already directs a missing-key lookup to `orch ticket list`. | Say which task failed and give a safe line to find a current ticket: “Couldn't open that ticket here. Next: `orch ticket list`.” Don't claim the ticket was deleted or disclose a different workspace. Preserve the error exit and JSON channel; checking a bad reference must not start a dashboard. |

### Evidence and limits

Baseline `5cce426b9`. The Focus boundary check called `orch_focus.needs.rows` with real synthetic record files, a stubbed alive check and ticket title, not 201 running helpers. The wall check called `liveWallWithNeeds` and `liveWallBands` in `web/pages/livewall.js`; it is a different path from the CLI needs collector. Factory evidence is the `follow` → `render` → `heading` path in `orch_factory/web/factory.js`; no claim of measured screen-reader speech.

For the shared control, compare `askReplacedBy` in dashboard `pages/tickets.js` with master `select.js`, `components.css` and the later `interaction.css`, loaded by the gallery, Factory and dashboard. On `--surface`, the border tokens calculate to **1.42:1** (`--border`) and **4.49:1** (`--input`); these are token comparisons, not a whole-page contrast verdict. The master sets `color-scheme: dark`; a second theme isn't required. Use the [WAI-ARIA listbox keyboard pattern](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) rather than inventing an omnibox.

Phone review used `ChatsListView.swift`, `SwipeToHide.swift`, `ChatScreens.swift`, and the existing `docs/images/iphone-questions.png` for dark-screen context, not as evidence of motion. Windows review traced `install.ps1` and `addons.update(after_install=True)`; it was not a Windows execution. Core `--help` and the Focus error were read from the checkout with a strict disposable home. No simulator, personal tickets, real helpers or install were needed.

### What the challenge changed

Claude Opus 5.5 challenged anonymized scenarios. We adopted its order-insertion test: keeping a row number is not keeping a person's place. We rejected a virtualized grid and a new search field: test the existing picker against a native baseline first. Moving through options must not fire a change event. On phone, removing motion must not remove the feedback that distinguishes Hide from cancel. We declined a Windows restore wizard, new exit codes and counts of failed add-ons: the installer has an exit status here, not a reliable inventory.

These drafts exclude rounds 1–3's intake, handover, Review, sign-in, outcomes, service recovery, Personal, Insights, repair status, Factory restart, browser handback, scheduling, first-run routes, Path, install-stage failures, triage, phone delivery/history, status-parser and general-help proposals. In particular, the new Windows draft starts **after** core installation succeeds.
