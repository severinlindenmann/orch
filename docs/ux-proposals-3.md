# Seven drafts for iPhone, Windows and the command line

**ORCH-1864 · 24 November 2026. Try the Windows command-location fix first.** Someone who installed orch successfully can follow its PowerShell instruction and still not be able to run it. Second, stop pointing people at a command that orch itself refuses when there are no tickets to review.

These are experiments, not shipped fixes or results from a user study. Each slug maps to one `f62-ux-<slug>.md` builder job. The last column is the decision test for that draft.

| Draft | Before | Proposed after | How to tell |
|---|---|---|---|
| 1. Run the installed copy (`windows-command-path`) | `install.ps1` uses `uv tool dir --bin` to run `orch.exe`, then checks a different, hard-coded `.local\bin` to print a persistent user Path edit. | If the installed copy isn't the one PowerShell would run, show a copyable command using the verified executable location, e.g. `& '…\Sales Tools\orch.exe' --version`. Say whether it works only by full path or also by name. | With a custom bin folder, spaces, an apostrophe or an older `orch` first on Path, the printed command runs the newly installed copy. No user or machine Path edit is required to try it. |
| 2. Don't start work on an empty list (`triage-next`) | A read-only `orch triage` printed “Tickets: 0”, “Nothing stands out”, then `Next: orch triage --start`. On an empty workspace, `triage.start` refuses before creating a ticket or starting a helper. | “No tickets in the selected lanes.” Finish with the read-only `Next: orch ticket list`. Don't imply the whole workspace is empty. | Zero rows and zero findings are **different**: cover an empty lane with tickets elsewhere, a nonempty quiet list and an actual finding. Reading any list starts nothing. |
| 3. Explain a failed phone message where it stays (`phone-not-sent`) | A failed bubble shows **Not sent**, **Retry**, **Discard**. The reason in the bubble is only a VoiceOver hint; the app can announce an error separately. | Beside the unsent message, show one short, safe recovery sentence that VoiceOver reads too. Use known facts, or “Try sending this message again” when no cause is known. Keep Discard distinct. | Return to the chat after transient feedback is gone: identify the affected message and retry just that one. An arbitrary server sentence never becomes receipt copy. Waiting offline is not failure. |
| 4. Name the Windows install step that stopped (`windows-install-stop`) | The two terminating wrappers say `uv install failed` and `uv tool install failed`. A person cannot tell whether orch itself was being installed. | Identify the failed step in PowerShell: “Couldn't set up the tool orch needs to install” versus “Couldn't finish installing orch”. Give one applicable recovery step; keep the underlying diagnostic available. | Force each exit independently in a disposable standard-user install. No success line, misleading `orch init`, elevation advice, guessed network cause or suggestion that tickets were erased. |
| 5. Correct the filter, not the command (`status-filter-error`) | `orch ticket list --status working` prints `"working" is not an orch ticket list command. Run orch ticket list --help.` But `ticket list` was right. | Name `--status` and its accepted values. For the familiar display word “Working”, show the actual spelling `orch ticket list --status active` as an example, without executing it. | A person can correct the filter in one more line. Bad values still exit 2 on stderr; a misspelled **command** still gets command help. |
| 6. Tell me what Earlier searched (`phone-earlier-search`) | **Search old chats** filters earlier days by message preview in this workspace's general chat. Zero matches leave a blank section when days exist. Finished groups below don't filter. | Label the scope, e.g. **Search earlier messages in this chat**. Within Earlier days, say “No matching earlier messages in this chat” and let the person clear the search. Keep Finished groups separate. | Search for a word found only in a finished group's title. That group is still reachable; the empty message doesn't deny its existence. Clearing restores the same days without leaving the screen. |
| 7. Give everyday help a starting point (`help-by-goal`) | `orch --help` introduces “tickets with evidence for any agent tool”; `ticket` is described as “tickets”, after service and maintenance commands. | Before the catalogue, show two useful lines for an existing workspace: “See your tickets: `orch ticket list`” and “See what needs your answer: `orch needs`”. Leave command help and `--help-all` intact. | At ordinary terminal width, both tasks are visible without scrolling; each example runs on an empty local workspace without starting anything. Someone looking for an advanced command can still find it. |

### Evidence and challenge

Baseline `b63515d3a`. The CLI examples above came from this checkout with a disposable project, a separate home and `ORCH_HOME_STRICT=1`; no real helper ran. Compare `workspace/src/orch/cli.py` (`build_parser`, `_Parser.error`), `triage.py` (`collect`, `list_text`) and `nextstep.py` (`_triage`). Windows findings are a source walk through `install.ps1`, **not** a Windows execution. Both concern reaching a working executable or understanding a failure, not round two's choice between basic and recommended setup.

The phone evidence is from `mobile/OrchMobile/Views/{ChatHistoryView,ChatParts,Receipts}.swift`, `ChatDay.search`, and the failure/queue branches in `Outbox.swift` and `AppModel.swift`. The mock onboarding simulator path is a baseline smoke, not a reproduction of those two edge states. Neither proposal changes the answer/review flow, performs a wider search, or changes delivery.

One independent challenge with **Claude Opus 5.5** moved the misleading Path instruction and empty-list helper prompt ahead of shortening help: following those instructions has a consequence beyond extra reading. We kept the stage-specific install failures but rejected “safe to retry” as a blanket promise for a reinstall. We rejected treating a missing connection as a failed send (it normally stays queued), and rejected an example for every subcommand: a longer help page would defeat the experiment. The common test is whether someone can take the *right next action*, not whether there are fewer words.
